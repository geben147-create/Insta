제 1부. BIOS · Ubuntu · Hermes · MiniMax.
전원이 꺼져 있다가 켜지고, 영상이 완성되기까지.

1. BIOS에서 설정 전 화면을 사진으로 보관한다. Advanced → ACPI Configuration에서 PCIE Devices Power On을 Enabled, Deep Sleep을 Disabled로 확인한다. RTC Alarm Power On은 By OS가 있다면 먼저 실제 지원 여부를 시험한다.

2. Ubuntu에서 timedatectl, sudo hwclock --show, cat /proc/driver/rtc 및 rtcwake를 점검한다. BIOS의 고정 시각과 운영체제의 UTC/KST 설정이 맞는지 확인한다.

3. 자동 종료를 연결하기 전에 3분 뒤 RTC 알람을 예약하고 수동 종료 후 실제 재부팅되는지 시험한다. 실패 시 수동 전원 버튼과 WOL 복구 경로를 남긴다.

4. systemd가 부팅 후 네트워크·시간 동기화·GPU·ComfyUI 준비를 확인하도록 구성한다. Hermes는 AI 작업만 담당하고, 파이프라인 제어와 재시도는 Python 실행기가 담당한다.

5. 중복 게시 방지를 위해 파일 잠금, 작업 ID, 단계별 상태 저장, 영상 해시, 재실행 규칙을 추가한다. 미검증 전원 명령이나 Hermes 전체 승인 해제는 금지한다.

6. MiniMax H3는 이미 성공한 작은 샘플을 기준으로 시작하고 RTX 3090의 VRAM/RAM과 타임아웃을 실측한다. 1080p나 전체 2K 제작을 곧바로 로컬 성공으로 가정하지 않는다.

중요한 추가 사항. 추가된 핵심: 부팅 원인/허용 시간대 검사, 중복 실행 잠금, root 소유 전원 제어 스크립트, RustDesk 원격 복구, 장애 알림.

제 2부. Instagram 업로드: API vs ADB.
자동 클릭과 공식 게시 권한은 서로 다릅니다.

1. 가장 먼저 Meta 공식 Instagram Graph API를 검증한다. 본인 소유 프로페셔널 계정은 적절한 앱 역할과 Standard Access 범위에서 개발 모드 시험이 가능한 경우가 있다.

2. Facebook Login 경로라면 연결된 Facebook 페이지와 권한을 확인한다. 이 경로는 지원되는 버전에서 rupload를 사용해 Ubuntu 로컬 MP4 바이너리를 업로드할 수 있다.

3. API는 컨테이너 생성 → 업로드 완료 FINISHED 확인 → media_publish → 게시된 media ID와 permalink 재조회로 처리한다. 컨테이너 생성만으로 성공 처리하지 않는다.

4. ADB·scrcpy·Phone Harness·ATV·FPV는 모바일 화면을 자동 조작할 수 있고 게시 버튼을 누르는 것도 기술적으로 가능하다. 그러나 비공식 UI 자동화의 탐지·계정 제한 위험이 없다는 보장은 없다.

5. share_to_feed=false는 비공개가 아니라 피드 동시 노출을 줄이는 옵션이다. 테스트에도 실제 공개 계정 게시 주의가 필요하다. 검수 중에는 게시 단계 직전에 중단한다.

6. Reels는 9:16, H.264, AAC, 23~60fps를 기준으로 검증한다. API 상한은 90초로 고정하지 않는다. 2026년 일부 Facebook Login 음악 API를 지원할 수 있으나 앱 내 모든 음악을 자유롭게 붙이는 것은 아니다.

중요한 추가 사항. 추천: 일반 릴스·캐러셀은 공식 API를 우선하고, 앱 고유 효과가 필요한 경우에만 사람의 확인 아래 휴대폰 경로를 사용합니다.

제 3부. 5만 자 TTS와 MP3 비용.
HTTPS는 재생 장소, TTS는 소리를 만드는 엔진.

1. GitHub Pages의 HTTPS 페이지는 무료 범위에서 MP3 파일을 재생한다. GitHub 자체가 자동으로 음성을 합성하지 않는다.

2. 브라우저 음성 읽기 버튼은 기기의 한국어 음성 엔진을 이용해 즉시 들어볼 수 있다. 이것은 MP3 파일 생성과 다르며 지원 음성·길이는 기기에 따라 달라진다.

3. Ubuntu의 Qwen3-TTS는 로컬에서 이미 Sohee 한국어 샘플을 만든 경로를 재사용한다. API 글자당 요금은 0달러지만 전력·시간이 든다.

4. 내 목소리 재현은 Qwen3-TTS Base 모델과 내가 동의한 참고 WAV 및 정확한 녹음 대본으로 별도 시험한다. CustomVoice의 Sohee와 내 목소리 복제는 서로 다른 모드다.

5. Google Cloud TTS는 현재 표시된 무료 할당량 안이라면 5만 자 합성료가 0달러일 수 있다. 무료 소진 후 5만 자 예시는 Standard/WaveNet 0.20달러, Neural2 0.80달러, Chirp 3 HD 1.50달러, Instant Custom Voice 3.00달러다.

6. Google Gemini 계열 음성 모델은 문자 수가 아닌 입력 텍스트 토큰 + 생성된 오디오 토큰으로 과금할 수 있다. Codex의 개발용 토큰과 로컬 Qwen3의 TTS 토큰을 같은 비용으로 취급하지 않는다.

중요한 추가 사항. 처음 30초를 로컬 Qwen3로 만들고 발음 확인 후 5만 자를 분할 생성하세요. 5만 자 파일은 길고 커질 수 있으니 조각별 검수와 보관 정책이 필요합니다.

제 4부. 실행 순서 · 기록 · 안전 종료.
처음부터 완전 무인 게시를 켜지 않습니다.

1. 1차 읽기 전용 진단: BIOS 사진, RTC 상태, WOL, RustDesk, Hermes 버전/설정, ComfyUI 상태를 PASS·FAIL·미확인으로 정리한다.

2. 2차 하드웨어 시험: RTC 예약 1회 실제 기상, WOL 수동 기상, 로그인 전 원격 접속을 각각 검증한다.

3. 3차 제작 시험: MiniMax 샘플 → ffprobe 규격 검사 → 음량·자막·검은 화면·첫/중간/끝 프레임을 확인한다.

4. 4차 인스타 시험: Meta 개발 계정 인증 후 공식 API로 승인된 시험 릴스 1건을 게시하고 permalink 확인까지 완료한다.

5. 5차 음성 시험: Qwen3 한국어 30초 MP3 → 직접 듣기 → 분할 합성 5만 자 → 파일 해시·길이 검수. 다음에 MP3를 GitHub Pages 경로에 넣는다.

6. 6차 최종 자동화: 작업 상태·게시 결과 저장, 원격 접속·GPU 작업·실패 대기 검사, 다음 RTC 예약의 실제 기록 검증 후에만 전원을 종료한다.

중요한 추가 사항. 기록은 Google Sheets에 날짜·상태·URL·처리량을, GitHub에는 설명·코드·변경 이력을, 로컬 디스크에는 원본 영상·오디오를 보존하는 구조가 좋습니다.
